## 2. 성능 측정

### 2.1 비교 대상

| 구분 | 프론트엔드 | Apps Script 백엔드 |
|---|---|---|
| 개선 전 | `main` @ `2e107ed` (2026-10-29 운영 상태) | 버전 34 (당시 운영 배포 @34를 측정용 임시 배포로 띄움, 측정 후 삭제) |
| 개선 후 | `main` @ `530b721` (현재 운영) | 운영 배포 @60 |

두 버전 모두 같은 OAuth 클라이언트(`651515712118-v387…`), 같은 Google 계정(조교 역할 `khk213624@gmail.com`), 같은 스프레드시트를 썼습니다.

### 2.2 방법

- 각 버전을 빌드해 `localhost:5173`에서 `vite preview`로 띄우고, 화면 없는 Chrome(헤드리스)을 개발자 도구 프로토콜(CDP)로 제어했습니다.
- 매 회 새 브라우저 프로필, 브라우저 캐시 끔, 앱 캐시(`cache_*`) 없이 로그인 토큰만 넣은 **첫 로그인 직후 상태**에서 시작했습니다.
- **대시보드 표시 시간:** 앱 주소를 연 시점부터 대시보드의 "위젯 추가" 버튼이 화면에 나타나고 "데이터를 불러오는 중" 표시가 없어질 때까지.
- **호출 수:** 같은 구간에서 `/api`(Apps Script 프록시)로 나간 요청 수.
- **JavaScript 전송량:** 같은 구간에서 내려받은 `.js` 파일의 전송 크기 합.
- **시트 ID 조회:** 로그인 직후 앱이 부르는 것과 같은 8개 이름으로 `getSpreadsheetIds`를 각 백엔드에 직접 호출(`curl`, 리디렉션 포함 전체 시간). 개선 후 백엔드는 요청자 토큰 확인(서버 측 인가) 시간까지 포함합니다.
- 측정 스크립트는 저장소에 포함하지 않았습니다(일회성).

### 2.5 한계

- 개발 PC 한 대, 한 계정(조교)으로 측정했습니다. 역할에 따라 대시보드 위젯과 미리 받는 데이터가 달라 시간이 다를 수 있습니다.
- 개선 전 버전은 넓은 범위(`drive` 등)를 요구하지만, 이번 측정은 개선 후 로그인으로 받은 토큰을 두 버전에 같이 넣었습니다. 같은 클라이언트에서 발급된 토큰이고 측정 구간의 화면에서 권한 오류는 없었습니다.
- 장부 저장(배치 쓰기)처럼 로그인 이후 작업의 시간은 재지 않았습니다.
