## ADR-001 Google Workspace를 플랫폼으로 쓴다

**상황:** 학과에는 서버를 운영할 예산과 인력이 없었습니다. 구성원은 모두 Google 계정을 쓰고, 학과 자료도 이미 Google Drive에 있었습니다.

**결정:** 로그인(OAuth), 저장(Sheets·Drive), 문서(Docs), 일정(Calendar), 메일(Gmail), 그룹(Groups)을 모두 Google Workspace에 맡기고, 업무 로직은 Apps Script에 둡니다.

**결과:**
- 서버·DB 비용이 0원이고, 새 계정을 만들 필요가 없습니다.
- 사용자는 결과물(문서, 장부)을 평소 쓰던 Google 화면에서 그대로 열 수 있습니다.
- 대가: Apps Script의 실행 시간(6분)과 호출 할당량 안에서 동작해야 하고, 응답이 일반 서버보다 느립니다. → [ADR-005](#adr-005-클라이언트-캐시와-2단계-프리페치)로 보완

## ADR-002 Google Sheets를 데이터베이스로 쓴다

**상황:** 관계형 DB를 두면 호스팅 비용과 운영 부담이 생깁니다. 운영자(조교)는 DB를 직접 다루기 어렵지만 스프레드시트는 다룰 수 있습니다.

**결정:** 스프레드시트 파일을 DB로, 시트를 테이블로 씁니다. 도메인마다 파일을 나눕니다(`hp_member`, `notice`, `workflow`, `student`, `staff`, 장부별 파일).

**결과:**
- 운영자가 시트를 열어 데이터를 직접 확인하고 고칠 수 있습니다.
- 파일 단위 Drive 공유로 접근 범위를 나눌 수 있습니다.
- 대가: FK·트랜잭션·동시성 제어가 없습니다. 무결성은 애플리케이션 코드가 지켜야 하고, 열 순서가 바뀌면 코드가 깨집니다([DATA_MODEL.md §6](./DATA_MODEL.md#6-알려진-불일치-정리-대상)).

## ADR-003 데이터 접근 경로를 두 갈래로 나눈다

**상황:** 모든 데이터를 Apps Script로 거치면 호출 할당량과 지연이 커집니다. 반대로 모든 데이터를 브라우저에서 직접 읽으면 권한 검사나 Drive 조작(폴더 생성, 권한 부여)을 할 수 없습니다.

**결정:**
- **Apps Script 경유:** 회원, 공지, 결재, 공유 문서처럼 배포자 권한으로 처리해야 하거나 여러 사용자가 공유하는 데이터
- **브라우저 직접(papyrus-db + 사용자 OAuth 토큰):** 캘린더, 학생·교직원, 장부 데이터, 개인 설정처럼 조회가 잦고 **Drive 공유 권한으로 접근을 통제할 수 있는** 데이터
- 브랜치 `feature/drive-file-scope`에서는 `papyrus-db`를 자체 모듈 `sheetsClient`로 바꾸고, 공유 파일의 Drive 조작(검색, 업로드, 복사)을 Apps Script 쪽으로 옮겼습니다([ADR-014](#adr-014-drive-범위를-drivefile로-줄이고-공유-파일은-apps-script가-다룬다)).

**결과:**
- 조회가 많은 화면이 빨라지고 Apps Script 호출이 줄었습니다.
- 대가: 같은 시트를 두 경로에서 다루면 열 순서 가정이 어긋날 수 있습니다(예산계획 시트). 접근 경로별 권한 모델이 달라 문서화가 필요합니다([SECURITY.md](./SECURITY.md)).

## ADR-004 Apps Script 앞에 Netlify Function 프록시를 둔다

**상황:** 브라우저에서 Apps Script 웹앱을 직접 호출하면 CORS 제약에 걸리고, 웹앱 URL이 번들에 노출됩니다.

**결정:** 배포 환경에서는 `/.netlify/functions/proxy`를 거쳐 호출합니다. 프록시는 서버 전용 환경변수 `APP_SCRIPT_URL`만 읽습니다. 로컬 개발에서는 Vite dev 서버 프록시(`/api`)가 같은 역할을 합니다.

**결과:**
- CORS 문제가 사라지고, 웹앱 URL이 클라이언트 코드에 들어가지 않습니다.
- Apps Script가 HTML 오류 페이지를 돌려줘도 프록시가 `{success:false}` JSON으로 바꿔 줘서 클라이언트 오류 처리가 단순해졌습니다.
- 대가: 요청마다 한 단계를 더 거칩니다. Netlify 대시보드의 환경변수 설정을 빠뜨리면 모든 API가 500을 반환합니다([RUNBOOK.md](./RUNBOOK.md)).
- 대가: Netlify 동기 함수는 약 10초에서 끊깁니다. Apps Script가 그보다 오래 걸리면 클라이언트는 응답 대신 Netlify 오류를 받습니다. 2026-10-29 측정에서 운영 배포의 `getSpreadsheetIds`가 49.4초 걸려, 사이트를 통한 첫 로딩은 시간 초과와 재시도를 반복했을 것으로 봅니다.

**보완 (브랜치 `feature/loading-performance`, 미병합):**
- 프록시가 Apps Script 호출을 약 9초에서 직접 끊고 504 `{success:false, error, retryable:true}`를 돌려줍니다. 클라이언트는 이 응답을 재시도 가능한 오류로 처리합니다.
- `APP_SCRIPT_URL`만 읽습니다. `VITE_APP_SCRIPT_URL`만 있으면 500입니다.
- 로그에는 HTTP 메서드와 `action`만 남기고, 요청 본문과 Apps Script URL은 남기지 않습니다.
- 느린 액션 자체는 프록시로 해결되지 않으므로 서버 쪽을 빠르게 만들었습니다([ADR-013](#adr-013-스프레드시트-id를-drive-검색-1회와-서버-캐시로-찾는다)).
- 남은 한계: 타임아웃은 응답 헤더를 받을 때까지만 적용되고, 본문 읽기는 제한하지 않습니다(위험 낮음).

## ADR-005 클라이언트 캐시와 2단계 프리페치

**상황:** 로그인 직후 화면마다 Apps Script를 따로 호출하자 첫 화면이 늦게 뜨고, 호출이 몰리면 429(할당량 초과)가 났습니다.

**결정:**
- 로그인 후 꼭 필요한 데이터(Phase 1)는 동시 8개씩 가져오고, 나머지(Phase 2)는 화면을 막지 않고 가져옵니다.
- 응답은 메모리 + localStorage 2단계 캐시에 데이터 종류별 TTL로 보관합니다.
- 쓰기가 성공하면 관련 캐시 키만 무효화하고 다시 가져옵니다.
- 429가 오면 해당 종류의 주기 동기화를 잠시 멈춥니다.

**결과:**
- 같은 데이터를 여러 화면에서 써도 호출은 한 번입니다.
- 대가: 캐시 무효화 규칙을 액션마다 관리해야 합니다. 캐시가 계정별로 분리되지 않아 로그아웃 시 정리가 필요합니다([STATUS.md](./STATUS.md#4-기술-백로그)).

**보완 (브랜치 `feature/loading-performance`, 미병합):**
- 같은 캐시 키의 조회가 진행 중이면 새 호출을 보내지 않고 진행 중인 요청을 함께 씁니다.
- `getSpreadsheetIds`·`getAccountingFolderId` TTL을 45분에서 6시간으로 늘렸습니다. ID는 세션과 무관하고 거의 바뀌지 않기 때문입니다. 대신 `getSpreadsheetIds` 결과에 빠진 ID(`null`, `notFound`)가 있으면 캐시하지 않고, 캐시에 남아 있던 불완전 결과도 버립니다.
- 재시도를 줄였습니다(타임아웃 60초·5회 → 시도마다 30초·2회). 쓰기 액션은 재시도하지 않아 중복 쓰기를 막습니다. 429는 예외로 `Retry-After`를 지켜 재시도합니다.
- `clearAllUserData`가 API 캐시도 비우게 했지만, 로그아웃 경로가 아직 이 함수를 부르지 않아 로그아웃 정리 과제는 남아 있습니다.
- 대가: 스프레드시트 파일을 교체하면 클라이언트 캐시(6시간)와 서버 캐시(6시간)를 둘 다 비워야 새 ID가 쓰입니다. 클라이언트는 헤더의 새로고침 버튼을 누른 뒤 브라우저를 새로고침하고(한 탭 안에서는 ID를 메모리에 기억), 서버는 `clearSpreadsheetIdCache()`를 실행합니다.

## ADR-006 폴더·시트 이름을 JSON 환경변수로 관리한다

**상황:** 처음에는 폴더·스프레드시트 이름이 코드 곳곳에 하드코딩되어 있었고, 환경변수도 이름마다 하나씩(V1) 늘어났습니다. 다른 학과나 테스트 환경에 설치하려면 코드를 고쳐야 했습니다.

**결정:** `VITE_FOLER_NAME`, `VITE_SPREADSHEET_NAME`, `VITE_SHEET_NAME`, `VITE_GROUP_EMAIL` 네 개의 JSON 환경변수로 묶습니다(V2). 값이 비거나 잘못되면 기본값과 병합합니다. Apps Script 쪽은 스크립트 속성으로 같은 이름을 관리합니다.

**결과:**
- 코드 수정 없이 새 환경을 세팅할 수 있습니다.
- 대가: 프론트(`.env`)와 Apps Script(스크립트 속성) 양쪽 값을 맞춰야 합니다. `VITE_FOLER_NAME`의 오타는 호환성 때문에 그대로 둡니다.

## ADR-007 가입은 사전 등록 + 승인제로 한다

**상황:** Google 계정만 있으면 누구나 로그인할 수 있으므로, 학과 구성원만 들어오게 막아야 했습니다.

**결정:** 관리자가 학번·이름을 미리 등록하고, 사용자는 일치하는 학번·이름으로 가입을 신청하며, 관리자가 승인합니다. 승인하면 역할에 맞는 Google 그룹에 추가해 Drive 공유 권한까지 함께 처리합니다. 관리자 권한은 별도 관리자 키로만 신청할 수 있습니다.

**결과:**
- 외부인 가입을 두 단계(사전 등록, 승인)로 막습니다.
- 대가: 학기 초마다 사전 등록 작업이 필요합니다. Workspace 관리자 권한이 없으면 그룹 추가가 실패하고 안내 메일로 대체됩니다.

## ADR-008 결재는 검토선과 결재선을 분리한다

**상황:** 학과 결재는 "내용을 확인하는 사람(검토)"과 "최종 승인하는 사람(결재)"이 다릅니다.

**결정:** 결재마다 `review_line`과 `payment_line`을 따로 두고, 검토가 모두 승인되어야 결재가 시작됩니다. 단계마다 승인·반려·보류를 지원하고, 모든 전이를 `workflow_history`에 남깁니다.

**결과:**
- 실제 학과 결재 흐름을 그대로 옮겼고, 단계별 처리 시간을 이력으로 측정할 수 있습니다(KPI).
- 대가: 상태가 7개로 늘어 전이 규칙이 복잡합니다([ARCHITECTURE.md §6.2](./ARCHITECTURE.md#62-결재-workflow_documentsworkflow_status)).

## ADR-009 장부마다 스프레드시트를 따로 만든다

**상황:** 학생회비, 행사비처럼 장부마다 볼 수 있는 사람이 다릅니다.

**결정:** 장부를 만들 때마다 `account/{장부명}/` 폴더, 장부 스프레드시트, `evidence/` 폴더를 새로 만들고, 지정한 사용자·그룹에만 공유합니다.

**결과:**
- Drive 공유 권한만으로 장부별 접근을 나눌 수 있습니다.
- 대가: 장부 목록을 보려면 폴더를 탐색해야 하고, 장부 스키마를 바꾸면 기존 장부 파일을 하나씩 마이그레이션해야 합니다.
- 브랜치 `feature/drive-file-scope`부터 장부 목록은 Apps Script가 만들고, `통장` 시트에 저장된 접근 대상에게만 보여 줍니다. Drive 공유가 저장된 대상과 어긋나면 `applyLedgerSharing`으로 다시 맞춥니다.

## ADR-010 라우터 없이 상태 기반으로 화면을 전환한다

**상황:** 같은 번들을 웹(Netlify)과 Electron 두 환경에서 실행해야 했습니다. 경로 기반 라우팅은 서버 리다이렉트 설정과 `file://` 환경을 각각 따로 맞춰야 합니다.

**결정:** `currentPage` 상태와 `?page=` 쿼리 파라미터로 화면을 바꾸고, `PageRenderer`가 `switch`로 페이지를 고릅니다. 페이지는 `React.lazy`로 나눠 불러옵니다.

**결과:**
- 웹과 Electron에서 같은 코드로 화면을 전환하고, 딥링크(`?page=announcement-view&announcementId=N`)도 됩니다.
- 대가: 라우트 단위 접근 제어가 없어 페이지 진입 시 권한을 따로 검사해야 합니다([STATUS.md](./STATUS.md#4-기술-백로그)).

**결정:** 같은 Vite 번들을 Electron으로 감싸 Windows(NSIS), macOS(dmg), Linux(AppImage)로 빌드할 수 있게 합니다. 기본 배포는 웹입니다.

## ADR-013 스프레드시트 ID를 Drive 검색 1회와 서버 캐시로 찾는다

> 상태: 채택, 브랜치 `feature/loading-performance`(미병합). 측정은 [TEST_PLAN.md §8](./TEST_PLAN.md#8-로딩-성능-개선-검증-2026-10-29-featureloading-performance).

**상황:** 앱은 로그인 직후 `getSpreadsheetIds`로 스프레드시트 이름 목록을 ID로 바꿔야 다음 단계로 넘어갑니다. 기존 Apps Script는 이름 하나마다 루트 폴더 트리 전체를 재귀 탐색했고(이름 8개면 8번), 결과를 캐시하지 않았습니다. 2026-10-29 운영 배포 @34에서 이 호출 한 번이 49.4초 걸렸고, Netlify 동기 함수 제한(10초)을 크게 넘었습니다.

**결정:**
- 루트 폴더를 한 번만 정합니다. 스크립트 속성 `ROOT_FOLDER_ID`가 실제로 열리는 폴더면 그것을, 아니면 `hp_member` 스프레드시트의 부모 폴더를 씁니다. 결과는 `CacheService`에 6시간 보관합니다. 브랜치 `feature/drive-file-scope`에서는 순서를 바꿔 `hp_member`의 부모 폴더를 먼저 쓰고(내 드라이브 최상위면 제외), `ROOT_FOLDER_ID`는 대체값으로만 씁니다. `ROOT_FOLDER_ID`가 다른 폴더를 가리켜 서버가 엉뚱한 트리를 보던 문제를 막기 위해서입니다.
- 찾을 이름 전체를 `DriveApp.searchFiles` **한 번**으로 검색합니다(구글 시트, 휴지통 제외, 제목 일치). 결과 중 **루트 폴더 아래에 있는 파일만** 씁니다.
- 찾은 ID는 `CacheService`에 6시간 보관합니다. 캐시 키에는 스크립트 속성 `SHEET_ID_CACHE_VERSION`이 들어갑니다.
- 캐시 무효화는 `clearSpreadsheetIdCache()`가 `SHEET_ID_CACHE_VERSION`을 1 올리고 루트 폴더 캐시를 지우는 방식입니다. `initializeSystem()` 끝에서도 자동으로 부릅니다.
- 검색으로 못 찾은 이름(검색 결과 0건이거나 루트 밖 파일만 있는 경우)과 검색 자체가 실패한 경우에는 기존 폴더 트리 탐색으로 한 번 더 찾습니다. 못 찾은 이름은 캐시하지 않습니다.
- 응답 형식은 그대로입니다: `{success, data:{이름: ID|null}, notFound?}`.

**결과:**
- 테스트 배포 @35에서 첫 호출 7.2초, 이후 2.9~3.7초로 줄었고, 운영 배포와 같은 ID를 돌려줬습니다.
- 다른 Apps Script 기능이 쓰는 `getSheetIdByName`도 같은 경로와 캐시를 씁니다.
- 대가: 파일을 교체·이동·이름 변경한 뒤 `clearSpreadsheetIdCache()`를 실행하지 않으면 최대 6시간 옛 ID가 반환됩니다([RUNBOOK.md RB-08](./RUNBOOK.md#rb-08-시트를-바꾼-뒤-옛-데이터나-빈-화면이-보임)).
- 대가: 루트 밖에 같은 이름의 시트가 많으면 검색 결과를 걸러 내느라 부모 폴더 확인이 늘어납니다(폴더별 결과를 한 실행 안에서 기억해 줄임).

## ADR-014 Drive 범위를 drive.file로 줄이고 공유 파일은 Apps Script가 다룬다

> 상태: 채택, 브랜치 `feature/drive-file-scope`(develop 병합 전). 인증 절차는 [OAUTH_PUBLISHING.md](./OAUTH_PUBLISHING.md).

**상황:** 웹 클라이언트가 `drive`(restricted)와 쓰지 않는 `gmail.compose`(restricted), `documents`를 요청하고 있었습니다. 이대로 OAuth 앱을 게시하려면 restricted 범위 인증과 매년 유료 보안 평가(CASA)가 필요합니다.

**결정:**
- 웹 클라이언트 범위를 `drive.file`, `spreadsheets`, `calendar.events`, `calendar.readonly`, `profile`, `email`로 줄입니다. 관리자 키 메일 요청에서도 액세스 토큰을 보내지 않습니다.
- `drive.file`로는 배포자 소유 공유 파일이 보이지 않으므로, 공지 첨부·본문 이미지 업로드, 공유 스프레드시트 ID 조회, 증빙 업로드, 장부 목록, 공유 양식 내보내기를 Apps Script(배포자 권한)가 맡습니다.
- 공유 양식으로 개인 문서를 만들거나 장부를 Excel로 내보낼 때는 Apps Script가 원본을 docx·xlsx로 내보내고(`exportTemplateFile`), 브라우저가 변환 업로드로 사용자 개인 폴더에 저장합니다.
- 개인 데이터는 공유 루트와 이름이 다른 개인 폴더 `hot_potato_personal/`에 둡니다. 이 폴더와 안의 파일은 앱이 만든 것이므로 `drive.file`로 접근할 수 있습니다.
- 시트 값 읽기·쓰기는 `spreadsheets` 범위로 계속 브라우저에서 직접 합니다.

**결과:**
- restricted 범위가 없어져 보안 평가(CASA) 없이 브랜드 인증과 민감한 범위 인증만 받으면 됩니다.
- 대가: Apps Script 호출이 늘고, 업로드 파일은 base64로 프록시를 거쳐 파일당 4MB로 제한됩니다.
- 대가: `exportTemplateFile`이 `UrlFetchApp`을 써서 배포자가 `script.external_request`를 한 번 더 승인해야 합니다.
- 대가: 예전 버전이 사용자 드라이브에 만든 파일은 새 범위에서 보이지 않습니다.
